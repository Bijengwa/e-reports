# Administrator bootstrap and break-glass reset

**Date:** 2026-08-18
**Status:** Approved design, not yet implemented
**Depends on:** `2026-08-17-ae-reports-environment-design.md`

---

## 1. Problem

The staff portal has a `users` table with a `password_hash` column and no way to put a row in it.
There is no seed script, no bootstrap route, and no password hashing anywhere in the codebase.
`POST /login` returns 503 and discards the body unread.

So the question is not "how do we lock down the existing seed" — there is nothing to lock down.
It is "how does the very first administrator come into existence, once, safely, and how do we get
back in when that account is lost".

## 2. Scope boundary

This slice delivers a credential contract. It is not the login slice.

| In scope | Out of scope (login slice) |
|---|---|
| `hashPassword`, temp password generation | `verifyPassword` |
| Insert of the first administrator | Login form, cookie, CSRF |
| Update of `password_hash` | Session creation |
| `DELETE FROM sessions` on reset | Staff-host session middleware |
| Setting `must_change_password = true` | Acting on that flag (forced redirect) |
| Audit entries for both commands | Role-based UI authorisation |

`verifyPassword()` is deliberately **not** written here. Neither command needs it, and unused code
is code nobody has run. When the login slice adds it, it must live beside `hashPassword` in
`src/auth/password.ts` and reuse the same parameter constants — the Argon2 parameters must never be
restated in a route.

## 3. Decisions

| Decision | Choice | Why |
|---|---|---|
| Bootstrap mechanism | CLI only | Whoever deploys always has shell on the VPS. A route that can mint an administrator is the most dangerous surface in the system; adding one for an emergency that cannot occur trades a real risk for an imaginary convenience. |
| Recovery | Two separate commands **plus** a two-administrator policy | Normal recovery is one administrator resetting another through the UI. The CLI reset is the last resort when both are lost. Keeping it out of `create` means the bootstrap guard never needs a loophole. |
| Password hashing | `@node-rs/argon2` (Argon2id) | Argon2id is the current OWASP recommendation. napi-rs ships musl prebuilds, so `node:24-alpine` needs no build toolchain — unlike the node-gyp `argon2` package. |
| First password | Generated by the CLI, printed once | Nothing is typed, so nothing enters shell history. The operator cannot choose a weak one. It dies at first sign-in via `must_change_password`. |
| Bootstrap guard | Advisory lock + conditional insert | See §7. |

## 4. Components

```
server/src/
  auth/password.ts        Argon2id parameters, hashPassword(), generateTempPassword()
  cli/admin.ts            Entry point: argument dispatch and exit-code mapping only
  cli/create-admin.ts     createAdmin(): the bootstrap
  cli/reset-password.ts   resetPassword(): break glass
```

New dependency: `@node-rs/argon2`.

### 4.1 Commands are functions; the entry point only translates

Both commands are plain functions returning a result value:

```ts
type CommandResult =
  | { status: "ok";       message: string; password: string }
  | { status: "refused";  message: string }
  | { status: "invalid";  message: string };
```

Anything unexpected is deliberately absent from that union: it propagates as a thrown exception,
which `admin.ts` catches and maps to exit 3. The three variants describe outcomes the command
anticipated; an exception is one it did not.

`admin.ts` maps that to a process exit code and nothing else. Integration tests call the functions
directly, never a subprocess — otherwise the argv parser gets exercised twice and the race test
loses access to the transaction handles it needs.

### 4.2 Configuration

The CLI calls the existing `loadConfig()`. There is no second configuration path.

Accepted cost: `loadConfig()` requires `PUBLIC_HOST` and `STAFF_HOST`, which the CLI does not use.
Both real invocation contexts (`docker compose exec`, and `tsx --env-file=.env` locally) supply
them, so a narrower CLI-only schema would add a maintenance burden for no gain.

### 4.3 Argon2id parameters

Named constants in `src/auth/password.ts`, defined once:

- `memoryCost`: 19456 KiB (19 MiB)
- `timeCost`: 2
- `parallelism`: 1

Output is a PHC string (`$argon2id$...`) stored whole in `users.password_hash`. The column already
exists and needs no migration.

### 4.4 Temporary password generation

20 characters drawn from the 32-character Crockford Base32 alphabet:

```
0123456789ABCDEFGHJKMNPQRSTVWXYZ
```

`I`, `L`, `O` and `U` are absent — the first three because they are misread as `1` and `0` when the
password is read aloud over a phone, `U` by Crockford's convention. 20 characters at 5 bits each is
100 bits of entropy.

**Why there is no modulo bias:** the alphabet has exactly 32 entries and 256 is an exact multiple of
32, so mapping each byte from `randomBytes(20)` through `byte % 32` is uniform. This is a property
of the arithmetic, not something to be established by sampling.

### 4.5 Database roles and grants

**A premise worth correcting before it reaches the code:** `docker compose exec app` does *not* run
as `ereports_app` today. `compose.yml` builds `DATABASE_URL` from `POSTGRES_USER`, which the
`postgres:18-alpine` image creates as superuser and owner of the database. The application connects
as the owner, and `ereports_app` does not exist at all — migration `0001` wraps its grants in
`IF EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'ereports_app')` and currently takes the `ELSE`
branch, raising a notice and granting nothing.

Everything `0001` grants, in full:

| Object | Privileges | To |
|---|---|---|
| `audit_log` | `SELECT`, `INSERT` | `ereports_app` |
| `audit_log_id_seq` | `USAGE`, `SELECT` | `ereports_app` |

It also revokes `UPDATE`, `DELETE` and `TRUNCATE` on `audit_log` from that role. **Nothing anywhere
grants `ereports_app` any privilege on `users` or `sessions`.**

The contract therefore has to be established, not merely written down:

1. **Production target:** application and CLI run as `ereports_app`. This is not true yet and this
   slice does not make it true — pointing `compose.yml` at that role would break every table with no
   grants (`reports`, `assessments`, `attachments`, `report_counters`). That is its own migration and
   its own change.

2. **This slice creates the role and grants only what these two commands touch**, in a new
   migration, so the integration tests can run the commands as `ereports_app` and prove the
   privileges are sufficient:

   | Object | Privileges |
   |---|---|
   | schema `public` | `USAGE` |
   | `users` | `SELECT`, `INSERT`, `UPDATE` |
   | `sessions` | `SELECT`, `DELETE` |
   | `audit_log` | `INSERT` — already granted by `0001` |
   | `audit_log_id_seq` | `USAGE`, `SELECT` — already granted by `0001` |

   `pg_advisory_xact_lock` requires no privilege. Adding a role and grants takes nothing away from
   the owner, so the running application is unaffected.

3. **Tests use two connections** (see §10.3). A single owner connection exercises a superset of
   production's privileges and proves nothing about them: the tests would pass while the container
   failed.

### 4.6 Input normalization and output language

`--email` is trimmed and lower-cased before Zod validation and before it reaches the unique index.
Without this, `A@tmda.go.tz` and `a@tmda.go.tz` become two rows, `23505` never fires, and the login
slice — which will look accounts up by a normalized address — reliably finds neither.

`--name` is trimmed only. Its capitalisation is the operator's to choose.

All CLI output is English. These commands are staff operations tooling; the `i18n` module exists for
the orange form and does not apply here.

## 5. Command: `create`

Everything below happens inside one transaction.

1. Validate `--email` and `--name` with Zod. Failure → `invalid`.
2. `pg_advisory_xact_lock(ADMIN_BOOTSTRAP_LOCK_KEY)`, declared once in `src/cli/create-admin.ts`:

   ```ts
   /** Arbitrary but permanent. Changing it reopens the race it exists to close. */
   const ADMIN_BOOTSTRAP_LOCK_KEY = 4_170_825_113n;
   ```

3. Generate the temporary password; hash it with Argon2id.
4. Conditional insert:

```sql
INSERT INTO users (email, full_name, role, password_hash, must_change_password, is_active)
SELECT $1, $2, 'administrator', $3, true, true
WHERE NOT EXISTS (SELECT 1 FROM users WHERE role = 'administrator')
RETURNING id
```

5. Zero rows → `refused`: *"An administrator already exists. Bootstrap is closed."*
6. One row → insert into `audit_log`: actor `null` (a system action, which the schema permits),
   action `user.bootstrap_created`, entity `user`, `after` carrying email, full name and role.
   **Never the hash.**
7. Commit, then write the password to stdout.

`must_change_password` is set **explicitly** even though the column already defaults to `true`. A
default can be changed by a future migration without `create` noticing; the row must be correct on
its own terms.

## 6. Command: `reset-password`

Inside one transaction:

1. Validate `--email`. No such user → `refused`.
2. Account has `is_active = false` → `refused`. A reset that cannot be used is a trap; the operator
   should learn this before reading a password down a phone line. Reactivation is a separate job and
   is not part of this slice.
3. Generate and hash a new temporary password.
4. `UPDATE users SET password_hash = $1, must_change_password = true WHERE id = $2`
5. `DELETE FROM sessions WHERE user_id = $2`
6. Insert `audit_log`: actor `null`, action `user.password_reset`.
7. Commit, then write the password to stdout.

The command works on **any** user, not only administrators. Restricting it would add no security —
the operator already holds `DATABASE_URL` — while removing legitimate use.

## 7. What the guard guarantees, and what it does not

`INSERT ... SELECT ... WHERE NOT EXISTS` alone is **not** race-free. Under `READ COMMITTED` the
`NOT EXISTS` subquery takes no lock, because there is no row to lock and PostgreSQL has no predicate
locking at that isolation level. Two concurrent transactions can both observe zero administrators
and both insert.

`pg_advisory_xact_lock` inside the same transaction is therefore **required**, not decorative. It is
what makes the conditional insert deliver the property it was chosen for. The lock is released
automatically at commit or rollback.

A unique constraint is not the answer. "Two administrators are allowed" is a statement about data;
"bootstrap runs once" is a statement about time, and the database cannot know which command opened
the transaction. No constraint can express it.

**Therefore:** the guard protects against accident — running the command twice, or two operators
acting at once. It does not protect against an operator with `DATABASE_URL`, who can insert an
administrator with plain SQL. That is not a defect. Anyone holding database credentials already owns
the system, and a "secret" known to the CLI would be theatre. This limitation belongs in `--help`
and the operations README, stated plainly, not hidden in a code comment.

## 8. Session contract

This slice deletes session rows, which only works if there is nothing else to delete.

**Contract:** every staff session is a row in `sessions`. The `__Host-` cookie carries an opaque
identifier and nothing more — no claims, no signed payload, no state that survives the row's
deletion.

The login slice must not break this. A JWT or a signed cookie carrying its own expiry would make
`reset-password` silently ineffective: the operator would believe the account was locked out while
the existing session kept working.

## 9. Error handling

| Exit | Meaning |
|---|---|
| `0` | Success |
| `1` | Refused for an expected reason — bootstrap closed, no such user, account inactive, email taken |
| `2` | Invalid input (Zod) |
| `3` | Unexpected — database unreachable, and anything else |

Separating `1` from `3` matters: "an administrator already exists" is an *answer*, not a crash, and
a deployment script can distinguish them (`create || [ $? -eq 1 ]`).

**Unique-violation handling.** On bootstrap the `NOT EXISTS` guard can pass — no administrator
exists — while the email collides with an existing non-administrator user. PostgreSQL raises
`23505` on `users_email_unique`. This is caught by error code (or constraint name) *before* the
general handler and reported as **exit 1**, message *"A user with that email already exists."* It
must not be reported as "Bootstrap is closed", which would be a lie, and must not be exit 3, because
it is a data conflict rather than a dead database. Any *other* unique violation stays exit 3.

**Two invariants.**

- The password never appears in an error message, a log line, or a stack trace. It is written with
  `process.stdout.write`, not through the application logger, so it cannot reach log aggregation.
- Printing happens strictly after commit, so a rolled-back row can never have its password printed.
  If `stdout.write` itself fails after a successful commit, the exit code stays **0** — the row
  exists, and reporting failure would be wrong.

## 10. Testing

The existing suite touches no database at all; `tests/doors.test.ts` says so explicitly. That is
fine for pure domain logic, and useless here: the guard is a property of PostgreSQL concurrency. A
mock asserting "we called insert with `WHERE NOT EXISTS`" proves the string was typed correctly, not
that the race is closed.

Testcontainers is unavailable — the development machine has no Docker and no WSL.

### 10.1 Two tiers

- `pnpm test` — unit tests always, integration tests wrapped in
  `describe.skipIf(!process.env.TEST_DATABASE_URL)`. Green on any machine.
- `pnpm test:integration` — **fails closed** when `TEST_DATABASE_URL` is absent. Without this, a CI
  run with no database would go green while silently skipping the race test, which is the
  self-congratulating test the tier exists to avoid.

CI that provisions PostgreSQL sets the variable and runs `test:integration`. Without that job, the
advisory lock is verified only on paper.

### 10.2 Test database safety

Before connecting, refuse to run when:

- `TEST_DATABASE_URL === DATABASE_URL`, or
- the database name does not end in `_test`.

The advisory lock is per-database. Failing closed prevents a stray test run from taking the
bootstrap lock — or truncating tables — in the development database.

### 10.3 Connections and teardown

Two connections, as set out in §4.5: the **owner** applies migrations and truncates, and
**`ereports_app`** runs the commands under test. Running the commands as the owner would exercise a
superset of production's privileges — the tests would pass while the container failed on a missing
grant.

`TRUNCATE users, sessions, audit_log RESTART IDENTITY CASCADE` between tests, on the owner
connection.

It must be `TRUNCATE`, not `DELETE`. Migration `0001` installs a `BEFORE UPDATE OR DELETE ... FOR
EACH ROW` trigger on `audit_log` that raises for **every** role including the owner. Row-level
triggers do not fire on `TRUNCATE`, so truncation succeeds where deletion cannot. `CASCADE` is
needed because `audit_log.actor_user_id` and `sessions.user_id` reference `users`.

Integration tests connect as the **owner** role. `TRUNCATE` on `audit_log` is revoked from
`ereports_app`, so a test database reached through the application role would fail teardown.

### 10.4 Integration cases (real PostgreSQL)

1. `create` against an empty `users` table produces exactly one administrator with
   `must_change_password = true`.
2. `create` a second time returns `refused` and adds no row.
3. `create` refuses when an administrator exists even though other, non-administrator users exist.
4. **Race:** two `createAdmin()` calls in `Promise.all`, each on its **own `ereports_app` client** —
   postgres.js cannot hold overlapping transactions on one connection, so two queries on one client
   would not race at all. Assert one `ok`, one `refused`, and
   `COUNT(*) FILTER (WHERE role = 'administrator') = 1`. The test imports
   `ADMIN_BOOTSTRAP_LOCK_KEY` rather than repeating its value.
5. `reset-password` deletes that user's sessions and leaves other users' sessions untouched.
6. `reset-password` refuses on an inactive account, and on an address with no user.
7. `audit_log` rows are written for both commands and contain neither the hash nor the password.
8. `create` with an email already held by a non-administrator returns `refused` with the unique
   message, creates no administrator, and writes no bootstrap audit entry.

### 10.5 Unit cases (no database)

- The alphabet has exactly 32 characters, all distinct, and contains none of `I`, `L`, `O`, `U`;
  generated passwords are 20 characters long. These properties are what make the mapping unbiased,
  so they are asserted directly rather than through a chi-square test over samples, which is noisy
  and weak.
- `hashPassword` returns a PHC string beginning `$argon2id$`.
- Zod rejects a malformed email and an empty name.

## 11. Operations

```json
"admin":     "node dist/cli/admin.js",
"admin:dev": "tsx --env-file=.env src/cli/admin.ts"
```

Production runs the compiled entry point; the runtime image ships `dist/` and not `src/`, so `tsx`
cannot be used there:

```
docker compose exec app node dist/cli/admin.js create --email=admin@tmda.go.tz --name="Full Name"
docker compose exec app node dist/cli/admin.js reset-password --email=admin@tmda.go.tz
```

Email and name travel in argv, which is fine — neither is secret. **The password never travels in
argv**, because argv is visible in `ps` and is recorded in shell history.

**Policy:** TMDA maintains two administrators from the first day. One losing access is then an
ordinary UI operation rather than a shell operation.

## 12. Follow-up noted, not addressed here

`.env.example` declares `SESSION_IDLE_MINUTES`, `SESSION_ABSOLUTE_HOURS`, `EMAIL_DRIVER` and
`SMS_DRIVER`, none of which `src/config.ts` parses. Zod strips unknown keys silently, so the values
are set and unused. The first two are needed by the login slice and should be added to the schema
there.
